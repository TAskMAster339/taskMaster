# Как добавить свою фичу

[Документация](README.md) · [Архитектура](ARCHITECTURE.md) · [Команды проверок](DEVELOPMENT.md#проверки)

## От идеи к изменению

1. Опишите пользовательское действие и ожидаемый результат, состояния ошибки и важные границы. Сверьте их с [действующими правилами](BEHAVIOR.md). Новую крупную возможность сначала обсудите в issue; существование Tauri-плагина само по себе не расширяет MVP.
2. Найдите похожую операцию по [карте кода](ARCHITECTURE.md#где-искать-код). Определите, меняются ли UI, доменная логика, данные или интеграция ОС. Запишите затрагиваемые контракты и проверку приёмки.
3. Для проверяемого поведения сначала воспроизведите требование тестом и убедитесь в ожидаемом падении. Затем внесите минимальное изменение, проверьте его и выполните рефакторинг. Для чистого текста и оформления не нужен искусственный unit-тест.
4. После итоговых проверок пройдите [завершение фичи](#завершение-фичи), затем отправьте PR по [CONTRIBUTING](../CONTRIBUTING.md). У агента локальные коммиты и внешние действия регулирует [AGENTS.md](../AGENTS.md).

## Если меняется действие над задачей или таймером

Проследите существующую операцию целиком, например `rename_task` или `create_timer`:

1. Добавьте валидацию/правило в Rust и операцию в соответствующий модуль `persistence/`. Изменение нескольких связанных записей должно быть транзакционным. При необходимости схемы следуйте [правилам миграций](ARCHITECTURE.md#хранилище-и-совместимость).
2. Добавьте или измените команду в `commands/`, регистрацию в `lib.rs`, запись `Commands` в `frontend/src/shared/tauri.ts` и DTO в `shared/types.ts`. При изменении аргументов проверьте все вызывающие места и mocks.
3. Реализуйте ввод, загрузку, успешное состояние и ошибку в контроллере фичи. Проверьте синхронизацию основного окна и оверлея, если действие видно в обоих. Не добавляйте событие, пока не определены его реальные подписчики.
4. Обновите переводы в `shared/messages.json` для русского, английского и японского, включая backend-ошибки. Русские строки служат ключами каталога; их изменение может затронуть и Rust, и frontend.

Для чисто визуального изменения обычно достаточно `frontend/src/styles/` и соответствующего контроллера; IPC и SQLite не меняются. Новый экран может потребовать обновить `View`, навигацию и композицию `app/view.ts`. Дизайн-решения сверяйте с [DESIGN.md](../DESIGN.md), а системные функции — с [руководством по платформам](PORTING.md).

## Как выбрать проверки

| Что меняется | Что проверить |
| --- | --- |
| Доменное правило, SQLite, время | Соответствующие Rust-тесты в `src-tauri/src/tests/`, границы и ошибки; для схемы — миграции и восстановление |
| Frontend-логика | `frontend/tests/unit/`; для DOM, клавиатуры и доступности — `frontend/tests/browser/` |
| IPC или DTO | Rust-тесты операции, frontend typecheck/build, mocks и browser-сценарий потребителя |
| Системная интеграция | Нативный запуск на затронутой ОС; сборка и mocks не заменяют runtime |
| Текст документации | Существование ссылок, команды по манифестам/CLI, навигация и согласованность с кодом |

Приватные Rust-тесты подключаются к своим модулям через `#[cfg(test)]` и `#[path = "../tests/..."]`; сохраняйте текущую структуру вместо расширения production API ради теста. Общие storage-тесты подключаются из `tests/mod.rs`. Browser fixtures используют mocks из `frontend/tests/fixtures/feature-fixture.mjs` и не обращаются к пользовательской SQLite-базе. Обычный `npm run dev` не подменяет Tauri IPC mocks автоматически.

Точные команды, установка Chromium и ручные сценарии находятся в [DEVELOPMENT.md](DEVELOPMENT.md#проверки). После локальных узких проверок убедитесь, что полный набор, требуемый для PR, проходит в CI; в описании отличайте выполненные проверки от недоступных.

## Завершение фичи

Документация обновляется по итоговому diff после проверки и очистки кода, до changelog и коммита. Это часть завершения фичи, в том числе когда она разработана с AI.

| Изменился результат | Где обновить |
| --- | --- |
| Пользовательское поведение, ограничения, ошибки | [BEHAVIOR.md](BEHAVIOR.md) |
| Модули, IPC, данные, миграции, события | [ARCHITECTURE.md](ARCHITECTURE.md) |
| Установка, команды, зависимости, проверки или релиз | [DEVELOPMENT.md](DEVELOPMENT.md); пользовательскую установку также в [README](../README.md) |
| Поддержка ОС или платформенный адаптер | [PORTING.md](PORTING.md) с указанием фактически проверенной среды |
| Визуальная система | [DESIGN.md](../DESIGN.md); при заметном изменении экранов — актуальные скриншоты README |
| Правила работы участников/агентов | [CONTRIBUTING.md](../CONTRIBUTING.md), [AGENTS.md](../AGENTS.md) и относящийся проектный навык |

Пройдите затронутый сценарий по инструкции как новый участник: ссылки должны открываться, команды — соответствовать текущему проекту, шаги — приводить к описанному результату. Если возможности проверить платформу нет, оставьте это явным ограничением. Новые страницы добавьте в [индекс](README.md). Не дублируйте справочники и не добавляйте запись ради записи, когда документация остаётся верной: в PR достаточно объяснить, почему обновление не нужно.

После сверки документации добавьте значимое изменение в `CHANGELOG.md` → `Unreleased`, проверьте итоговый diff и создайте коммит только своей итерации. В PR перечислите обновлённые документы или обоснование отсутствия изменений, команды и результаты проверок, оставшиеся ограничения.
