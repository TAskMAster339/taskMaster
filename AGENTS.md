# Инструкции для AI-агентов

## Проект

taskMaster — локальный персональный менеджер задач для Windows. Отображаемое имя приложения — `taskMaster`; действующие продуктовые правила описаны в `docs/BEHAVIOR.md`, визуальная система — в `DESIGN.md`.

Перед изменением поведения читай относящиеся к нему разделы `docs/BEHAVIOR.md` и при необходимости обновляй их. Не добавляй функции сверх MVP без прямого запроса пользователя.

## Стек и границы

- Desktop MVP: Tauri 2, Rust для доменной логики и системных интеграций, TypeScript/HTML/CSS без UI-фреймворка, SQLite через Rust.
- Приложение локальное и offline-first. Не добавляй облако, аккаунты, аналитику, телеметрию или сетевые вызовы.
- Доменные правила, валидация, SQLite и системный lifecycle принадлежат Rust. Frontend отвечает за отображение и ввод и обращается к backend через небольшие типизированные Tauri-команды.
- Сохраняй ручной порядок задач. Не превращай очередь в календарную временную шкалу.
- Автоархивация настраивается в часах (1–8760, по умолчанию 24) и сохраняет задачу и историю. Восстановление из архива даёт новый срок и возвращает задачу в конец очереди; см. `docs/BEHAVIOR.md`.
- Ограничивай capabilities Tauri минимально необходимыми командами и плагинами. Для новых Tauri API сверяй актуальную официальную документацию, особенно платформенную поддержку и разрешения.

## Текст интерфейса

- Пиши коротко и предметно. Не добавляй слоганы, мотивационные подписи, очевидные пояснения и дублирующие счётчики.
- Не используй формулировки вроде «Порядок задаёте вы», «Ручной порядок», «Отличная работа» и «Осталось» рядом с очевидным счётчиком, если пользователь или `docs/BEHAVIOR.md` явно этого не требует.
- Показывай текст только для понятного действия, состояния, ошибки или требований доступности. Не придумывай дополнительный микрокопирайт ради заполнения пустого места.

## Навыки проекта

Используй подходящий навык, когда задача попадает в его область:

- `$taskmaster-tauri-rust` — Rust backend, модель и миграции SQLite, Tauri commands, tray, overlay, notifications, timer, lifecycle или persistence.
- `$taskmaster-ui` — создание или изменение экранов, компонентов, состояний, клавиатурного управления или тем.
- `$taskmaster-design` — проработка визуального направления, структуры экранов, дизайн-токенов и состояний до или во время UI-реализации.
- `$taskmaster-tdd` — изменение поведения, для которого требуется тест-first workflow: сначала проверяемое требование и падающий тест, затем реализация.
- `$taskmaster-desktop-verification` — проверка кода, сборки/установщика, системных интеграций Windows или релизной готовности.
- `$taskmaster-docs` — сопровождение README и `docs/`, проверка документации по итоговому diff и обновление инструкций после завершения фичи; файл `.agents/skills/taskmaster-docs/SKILL.md`.

При разработке UI используй `$taskmaster-design` для дизайн-решений и `$taskmaster-ui` для реализации; можно подключать оба к одной задаче. Используй `$taskmaster-tdd` для тестируемого поведения, а verification skill — для широких или платформенных проверок. В конце каждой фичи используй `$taskmaster-docs` для сверки документации с результатом. Для небольших изменений документации UI/Rust/TDD/verification навыки не требуются. Не загружай все навыки без необходимости.

## Качество и рабочий процесс

- Сначала осмотри текущее состояние и локальные инструкции; не предполагай, что каталоги или команды из ТЗ уже существуют.
- До добавления зависимости проверь, решает ли она конкретное требование и поддерживает ли Windows MVP; не добавляй библиотеку «на будущее» без необходимости.
- Новое поведение доменного уровня сопровождай тестами на граничные случаи, если в репозитории уже доступна тестовая инфраструктура. Передавая результат, укажи реально запущенные проверки и их итоги; не выдавай компиляцию за проверку Windows runtime.
- Не скрывай ошибки сохранения, восстановления, миграций или системных разрешений. Не перезаписывай повреждённую базу пустой.
- Сохраняй незакоммиченные изменения пользователя и не включай посторонние файлы в свою итерацию.
- После каждой реализованной фичи добавляй краткую запись в `CHANGELOG.md` в секцию `Unreleased`. Перед релизом проверь, что секция содержит изменения. После успешной публикации перенеси её содержимое под заголовок выпущенной версии и даты, оставив пустую `Unreleased`; сохраняй историю предыдущих релизов.

### Цикл разработки фичи

Каждую фичу выполняй отдельной завершённой итерацией. Если запрос содержит несколько независимых фич, разбей работу на небольшие последовательные итерации и не начинай следующую до завершения текущей.

1. **Зафиксируй объём.** Сверь поведение с `docs/BEHAVIOR.md`, сформулируй критерии приёмки и определи затрагиваемые части приложения. Не добавляй соседний функционал.
2. **Добавь тест первым, когда он полезен.** Для новой доменной логики, исправления ошибки и поведения с важными границами создай проверку до реализации; запусти её и убедись, что она падает именно по ожидаемой причине. Для чисто визуальной правки, документации или тривиального изменения без значимого проверяемого поведения не создавай искусственный тест — укажи подходящую ручную проверку.
3. **Реализуй минимальное решение.** Сохраняй существующие архитектурные границы и делай только изменения, нужные для критериев этой фичи.
4. **Проверь результат.** Запусти узкие тесты и проверки затронутых модулей, затем сборку или интеграционную проверку, когда она доступна и нужна. Системные функции Windows проверяй в Windows; не считай Linux/WSL-сборку подтверждением Windows runtime.
5. **Очисти код.** После успешных проверок удали временный код, лишние зависимости и дублирование; проведи рефакторинг без изменения поведения и повторно запусти релевантные проверки. Проверь diff на несвязанные изменения.
6. **Сверь и обнови документацию.** Примени `$taskmaster-docs` к итоговому diff после реализации, проверок и рефакторинга. По таблице в `docs/ADDING_FEATURES.md` обнови затронутые продуктовые правила, архитектуру/IPC/данные, команды, платформенные ограничения, дизайн и инструкции. Проверь ссылки, примеры и соответствие описанного реальным результатам; новые страницы включи в `docs/README.md`. Сохраняй README кратким. Если изменения не нужны, укажи почему в итоговом отчёте или PR; не меняй документы ради отметки. Фича не завершена, пока эта сверка не выполнена.
7. **Обнови `CHANGELOG.md`.** Добавь пользовательски значимое изменение в `Unreleased`, сгруппировав его под `Добавлено`, `Изменено` или `Исправлено`. Не добавляй в changelog служебные правки документации, если они не меняют рабочий процесс пользователя или разработки.
8. **Зафиксируй итерацию коммитом.** После успешных обязательных проверок и сверки документации создай локальный коммит только с файлами этой фичи, связанными документами и её changelog-записью. Используй краткое предметное сообщение, например `feat: add task reorder` или `fix: archive expired tasks`. Не коммить незавершённую фичу, известные провалы проверок или посторонние изменения; если обязательная проверка заблокирована окружением, сообщи об этом и не выдавай итерацию за завершённую.
9. **Переходи к следующей фиче.** Кратко сообщи, что вошло в коммит, какие проверки прошли или были недоступны и какие документы обновлены (либо почему обновление не потребовалось), и только затем начинай следующую независимую итерацию.

### Релизы

- Релиз запускается вручную через GitHub Actions с default branch после успешных release-проверок и заполнения `CHANGELOG.md`.
- Workflow собирает Windows `.exe`, публикует отдельный version/date release и обновляет release с тегом `latest`.
- После успешной публикации workflow готовит PR, который архивирует содержимое `Unreleased` под версией и датой релиза, оставляя заголовок `Unreleased` пустым. Проверь и влей этот PR перед следующей публикацией. Не очищай весь файл и не теряй историю.
- При ошибке публикации до подготовки PR оставь записи `Unreleased` на месте; исправь причину и повторно запусти workflow.

Этот цикл разрешает локальные коммиты для запрошенных фич в рамках проекта. Не выполняй `push`, не меняй удалённый репозиторий и не переписывай опубликованную историю без отдельного прямого запроса.

## Windows и WSL

При работе из WSL используй фактический путь к корню репозитория в Linux-среде; не предполагай конкретную букву диска или точку монтирования. Поведение Windows tray, уведомлений, автозапуска, окон и установщика проверяется в нативной Windows-среде. WSL/Linux-сборка не является доказательством корректной работы Windows-сборки. Перед Windows packaging проверь актуальные Tauri prerequisites, Windows MSVC toolchain и WebView2.

## Документы

- `README.md` — описание, скриншоты, установка и быстрый старт.
- `docs/README.md` — точка входа и навигация по документации разработчика.
- `docs/BEHAVIOR.md` — действующие продуктовые правила и ограничения.
- `docs/DEVELOPMENT.md` — окружение, сборка, проверки, диагностика запуска и релизы.
- `docs/ARCHITECTURE.md` — модули, IPC, события, данные и миграции.
- `docs/ADDING_FEATURES.md` — разработка своей фичи и завершение с обновлением документации.
- `docs/PORTING.md` — подготовка Linux/macOS, карта адаптации и статус поддержки ОС.
- `DESIGN.md` — визуальная система и доступность.
- `.agents/skills/*/SKILL.md` — повторяемые рабочие процессы для конкретных типов задач.
