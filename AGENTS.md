# Инструкции для AI-агентов

## Проект

taskMaster — локальный персональный менеджер задач для Windows. Отображаемое имя приложения — `taskMaster`; продуктовые правила задаются в `ТЗ.md`.

`ТЗ.md` — источник истины для продуктового поведения. Перед изменением поведения читай относящиеся к нему разделы и при необходимости обновляй ТЗ. Не добавляй функции сверх MVP без прямого запроса пользователя.

## Стек и границы

- Desktop MVP: Tauri 2, Rust для доменной логики и системных интеграций, TypeScript/HTML/CSS без UI-фреймворка, SQLite через Rust.
- Приложение локальное и offline-first. Не добавляй облако, аккаунты, аналитику, телеметрию или сетевые вызовы.
- Доменные правила, валидация, SQLite и системный lifecycle принадлежат Rust. Frontend отвечает за отображение и ввод и обращается к backend через небольшие типизированные Tauri-команды.
- Сохраняй ручной порядок задач. Не превращай очередь в календарную временную шкалу.
- Архивирование по истечении 48 часов перемещает задачу из активного представления, но не удаляет её или историю. Учитывай правила восстановления из `ТЗ.md`.
- Ограничивай capabilities Tauri минимально необходимыми командами и плагинами. Для новых Tauri API сверяй актуальную официальную документацию, особенно платформенную поддержку и разрешения.

## Навыки проекта

Используй подходящий навык, когда задача попадает в его область:

- `$taskmaster-tauri-rust` — Rust backend, модель и миграции SQLite, Tauri commands, tray, overlay, notifications, timer, lifecycle или persistence.
- `$taskmaster-ui` — создание или изменение экранов, компонентов, состояний, клавиатурного управления или тем.
- `$taskmaster-design` — проработка визуального направления, структуры экранов, дизайн-токенов и состояний до или во время UI-реализации.
- `$taskmaster-tdd` — изменение поведения, для которого требуется тест-first workflow: сначала проверяемое требование и падающий тест, затем реализация.
- `$taskmaster-desktop-verification` — проверка кода, сборки/установщика, системных интеграций Windows или релизной готовности.

При разработке UI используй `$taskmaster-design` для дизайн-решений и `$taskmaster-ui` для реализации; можно подключать оба к одной задаче. Используй `$taskmaster-tdd` для тестируемого поведения, а verification skill — для широких или платформенных проверок. Для небольших изменений документации эти навыки не требуются. Не загружай все навыки без необходимости.

## Качество и рабочий процесс

- Сначала осмотри текущее состояние и локальные инструкции; не предполагай, что каталоги или команды из ТЗ уже существуют.
- До добавления зависимости проверь, решает ли она конкретное требование и поддерживает ли Windows MVP; не добавляй библиотеку «на будущее» без необходимости.
- Новое поведение доменного уровня сопровождай тестами на граничные случаи, если в репозитории уже доступна тестовая инфраструктура. Передавая результат, укажи реально запущенные проверки и их итоги; не выдавай компиляцию за проверку Windows runtime.
- Не скрывай ошибки сохранения, восстановления, миграций или системных разрешений. Не перезаписывай повреждённую базу пустой.
- Сохраняй незакоммиченные изменения пользователя и не включай посторонние файлы в свою итерацию.

### Цикл разработки фичи

Каждую фичу выполняй отдельной завершённой итерацией. Если запрос содержит несколько независимых фич, разбей работу на небольшие последовательные итерации и не начинай следующую до завершения текущей.

1. **Зафиксируй объём.** Сверь поведение с `ТЗ.md`, сформулируй критерии приёмки и определи затрагиваемые части приложения. Не добавляй соседний функционал.
2. **Добавь тест первым, когда он полезен.** Для новой доменной логики, исправления ошибки и поведения с важными границами создай проверку до реализации; запусти её и убедись, что она падает именно по ожидаемой причине. Для чисто визуальной правки, документации или тривиального изменения без значимого проверяемого поведения не создавай искусственный тест — укажи подходящую ручную проверку.
3. **Реализуй минимальное решение.** Сохраняй существующие архитектурные границы и делай только изменения, нужные для критериев этой фичи.
4. **Проверь результат.** Запусти узкие тесты и проверки затронутых модулей, затем сборку или интеграционную проверку, когда она доступна и нужна. Системные функции Windows проверяй в Windows; не считай Linux/WSL-сборку подтверждением Windows runtime.
5. **Очисти код.** После успешных проверок удали временный код, лишние зависимости и дублирование; проведи рефакторинг без изменения поведения и повторно запусти релевантные проверки. Проверь diff на несвязанные изменения и обнови документацию, если изменились интерфейсы или продуктовые правила.
6. **Зафиксируй итерацию коммитом.** После успешных обязательных проверок создай локальный коммит только с файлами этой фичи. Используй краткое предметное сообщение, например `feat: add task reorder` или `fix: archive expired tasks`. Не коммить незавершённую фичу, известные провалы проверок или посторонние изменения; если обязательная проверка заблокирована окружением, сообщи об этом и не выдавай итерацию за завершённую.
7. **Переходи к следующей фиче.** Кратко сообщи, что вошло в коммит, какие проверки прошли или были недоступны, и только затем начинай следующую независимую итерацию.

Этот цикл разрешает локальные коммиты для запрошенных фич в рамках проекта. Не выполняй `push`, не меняй удалённый репозиторий и не переписывай опубликованную историю без отдельного прямого запроса.

## Windows и WSL

При работе из WSL используй фактический путь к корню репозитория в Linux-среде; не предполагай конкретную букву диска или точку монтирования. Поведение Windows tray, уведомлений, автозапуска, окон и установщика проверяется в нативной Windows-среде. WSL/Linux-сборка не является доказательством корректной работы Windows-сборки. Перед Windows packaging проверь актуальные Tauri prerequisites, Windows MSVC toolchain и WebView2.

## Документы

- `ТЗ.md` — продуктовые требования, модели поведения, архитектурные границы и приёмка.
- `README.md` — краткое описание и состояние проекта.
- `.agents/skills/*/SKILL.md` — повторяемые рабочие процессы для конкретных типов задач.
